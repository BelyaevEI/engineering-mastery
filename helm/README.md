# Helm Chart (чарт)

Helm — это менеджер пакетов для Kubernetes. Если проводить аналогию с миром программирования или Linux, то Helm — это `apt`, `yum` или `npm`, но для Kubernetes-манифестов. А чарт — это сам пакет (как `.deb` или `.tgz`).

**Простыми словами:** чарт содержит готовые шаблоны YAML-файлов, необходимые для развертывания приложения (или базы данных, или целого стека микросервисов) в кластере Kubernetes.

Давайте разберем подробно, из чего он состоит, как работает и зачем нужен.

---

## 1. Проблема, которую решает Helm

До Helm процесс деплоя выглядел так:

- У вас есть куча YAML-файлов: `deployment.yaml`, `service.yaml`, `ingress.yaml`, `configmap.yaml` и т.д.
- Чтобы развернуть приложение на тестовом стенде, вы пишете одни значения. Чтобы развернуть на продакшене — другие (другие пароли, реплики, ресурсы).
- Приходилось либо копировать файлы и править их руками, либо писать сложные скрипты.

**Helm решает это через шаблонизацию и управление релизами.**

---

## 2. Структура Helm-чарта

Когда вы создаете новый чарт командой `helm create mychart`, генерируется следующая файловая структура:

```
mychart/
├── Chart.yaml          # Метаданные чарта
├── values.yaml         # Значения по умолчанию для шаблонов
├── charts/             # Зависимости (другие чарты)
├── templates/          # Папка с шаблонами Kubernetes-манифестов
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── _helpers.tpl    # Файл с вспомогательными шаблонами (функциями)
│   ├── NOTES.txt       # Сообщение, которое выводится после установки
│   └── ... (hpa, ingress, serviceaccount и т.д.)
└── .helmignore         # Файлы, игнорируемые при упаковке (аналог .gitignore)
```

### Разберем ключевые элементы

#### `Chart.yaml`

Это «паспорт» чарта. Обязательными полями являются `apiVersion` и `name`.

```yaml
apiVersion: v2        # Версия API Helm (v2 для Helm 3)
name: my-app          # Имя чарта
version: 0.1.0        # Версия самого чарта (SemVer)
appVersion: "1.16.0"  # Версия приложения, которое упаковано внутри
description: A simple web app
```

#### `values.yaml`

Самый важный файл. Здесь хранятся значения переменных по умолчанию. Шаблоны используют эти значения, чтобы сгенерировать готовые манифесты.

```yaml
replicaCount: 1

image:
  repository: nginx
  tag: latest
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80
```

#### `templates/`

Здесь лежат шаблоны. Они написаны на смеси YAML и Go-шаблонов.

**Пример `templates/deployment.yaml`:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "mychart.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ include "mychart.name" . }}
  template:
    spec:
      containers:
        - name: {{ .Chart.Name }}
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          ports:
            - containerPort: {{ .Values.service.port }}
```

Всё, что в двойных фигурных скобках `{{ }}`, — это команды шаблонизатора, которые подставят значения из `values.yaml`.

## 3. Основные концепции и команды

### Установка (Install)

Когда вы запускаете чарт, создается **Релиз** (Release) — это экземпляр чарта, работающий в конкретном кластере и namespace.

```bash
helm install my-release ./mychart
```

Здесь `my-release` — имя релиза. Вы можете установить один и тот же чарт 10 раз с разными именами (например, `dev-web`, `prod-web`).

### Переопределение значений

Просто установить — недостаточно. Нужно передать свои настройки. Для этого есть 3 способа (в порядке приоритета):

1. **`--set`**:  
   ```bash
   helm install my-release ./mychart --set replicaCount=5
   ```

2. **Свой `values`-файл**:  
   ```bash
   helm install my-release ./mychart -f my-values.yaml
   ```

3. **Значения по умолчанию** из `values.yaml` самого чарта.

### Обновление (Upgrade)

Если нужно изменить количество реплик или образ, вы не трете поды руками, а выполняете:

```bash
helm upgrade my-release ./mychart -f new-values.yaml
```

Helm вычислит разницу и применит изменения (например, обновит поле `replicas` в `Deployment`).

### Откат (Rollback)

Если обновление сломалось, Helm хранит историю и позволяет откатиться.

```bash
helm rollback my-release 1  # Откат к первой версии релиза
```

### Удаление (Uninstall)

```bash
helm uninstall my-release
```

Удалит всё, что было создано этим релизом.

## 4. Встроенные объекты и переменные

В шаблонах доступна не только конструкция `.Values`, но и предопределенные объекты, начинающиеся с заглавной буквы:

- **`.Release`**: Информация о релизе (`Name`, `Namespace`, `IsUpgrade` и т.д.).
- **`.Chart`**: Содержимое `Chart.yaml`.
- **`.Files`**: Позволяет вставить в `ConfigMap` содержимое внешнего файла (например, скрипт или конфиг).
- **`.Capabilities`**: Информация о кластере (версия Kubernetes, наличие API-ресурсов).

---

## 5. Зависимости (Subcharts)

Если вашему приложению нужна база данных Redis, вам не нужно писать чарт для Redis самому. Вы можете указать его как зависимость в `Chart.yaml`:

```yaml
dependencies:
  - name: redis
    version: "17.x.x"
    repository: "https://charts.bitnami.com/bitnami"
```

Затем выполнить `helm dependency update`, и чарт Redis скачается в папку `charts/`. Вы сможете настраивать Redis через `values.yaml` своего основного чарта, используя префикс `redis: ...`.

---

## 6. Хранилища чартов (Chart Repositories)

Это как Docker Hub, но для чартов. Это просто HTTP-сервер, который отдает упакованные `.tgz` архивы и файл `index.yaml`.

Самые популярные:

- **Bitnami** — огромная библиотека проверенных чартов для всего: WordPress, MySQL, Kafka.
- **Artifact Hub** — поисковик по чартам, операторам, плагинам.

## Итог: Зачем это нужно?

- **Повторное использование**: Один раз описал шаблон — развернул на dev/stage/prod.
- **Управление сложностью**: Одна команда вместо 10 кусков YAML.
- **Версионирование**: Вы точно знаете, какая версия приложения и какая версия конфигурации развернута.
- **Экосистема**: Не нужно писать чарты для типовых вещей (Nginx, Prometheus, PostgreSQL), они уже написаны и протестированы сообществом.
